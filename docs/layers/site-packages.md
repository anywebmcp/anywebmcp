# Site packages layer

`packages/sites/*` contains one package per supported website. A site package can expose different WebMCP tool sets for different areas of the same website based on the current URL.

Each package owns:

- Domain match patterns.
- Path match patterns that determine which WebMCP tools are available for the current URL.
- WebMCP tool definitions.
- Page context and selectors.
- UI, official API, or internal API adapters.

The X package lives at `packages/sites/x`. It captures X's GraphQL responses for structured reads and can publish through the signed-in web client's `CreateTweet` mutation without interacting with X's DOM.

The LinkedIn package lives at `packages/sites/linkedin`. It reads the virtualized feed through bounded DOM scans and scrolling, keeps stable references to recently observed posts, and can insert a verified comment draft for manual review without submitting it.

## Package structure

```text
packages/sites/<site>/
  README.md       Site-specific documentation
  BENCHMARKS.md   WebMCP versus browser-only benchmark results
  package.json    Package metadata and dependencies
  src/
    index.ts      Site manifest and package entry point
    tools/        WebMCP tool definitions
    api/          Optional website API adapters
```

A package can add other directories under `src` when its implementation requires them. Its `README.md` is the source of truth for supported domains and paths, available tools, implementation details, setup, and site-specific limitations. Record performance and token comparisons in `BENCHMARKS.md` following the [benchmarking process](../benchmarking-site-tools.md).
